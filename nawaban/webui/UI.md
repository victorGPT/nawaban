# UI source and NAWABAN boundary

The frontend's styled component layer is shadcn/ui on the Base UI registry, generated by `npx shadcn@latest add <name>` into `src/components/ui/`. `components.json` pins style `base-nova`. Semantic themes and typography live in `src/styles`; `src/styles/shadcn-tokens.css` aliases shadcn's token vocabulary onto them so the generated components inherit the existing palette in both themes. Calendars use DayPicker with `@internationalized/date` values, and tables use semantic HTML. See [AGENTS.md](AGENTS.md) for the layering rules.

## Component provenance

| Surface | Sources |
| --- | --- |
| Navigation and filters | `application/navigation/nav-item`, `application/theme/theme-toggle`, `application/select/module-select`, `application/date-picker/*`, ui `input`, `select`, `popover`, `button` |
| Cards, module nodes and tags | `application/settings/settings-rows`, ui `button`, `badge` (counter and status chip), local `StatusDot` |
| List and detail properties | ui `table` + `application/table/action-row`, `application/settings/settings-rows` |
| Detail and answers | ui `dialog` (adapted to a side sheet by `NawabanDialog`), `application/radio/radio-card`, ui `textarea`, `radio-group`, `checkbox`, `switch` |
| Notices and long text | ui `toast` + `application/notification/notice-card`, ui `tooltip` |

Business sections, Markdown, layout grids, module statistics and SVG dependency wires compose these sources. The isolated `interaction-fixture.html` exercises the production `NawabanDialog` and base controls without backend calls and is excluded from the production entry.

## Hand edits to generated files

Generated files are edited in place, the normal shadcn way, when the design needs a variant shadcn does not ship. Each carries a `BoardUI delta to the generated base-nova …` comment. Re-running the CLI for a component means re-applying its deltas.

| File | Delta | Why |
| --- | --- | --- |
| every `ui/*.tsx` | `import { cn } from "cn"` → `@/lib/utils` | the project's `cn` extends tailwind-merge with the composite `text-*` utilities; the stock one drops them next to a color |
| `button.tsx` | `button-press-motion` replaces `transition-all` + `active:translate-y-px` | keeps the press scale |
| `button.tsx` | `default`, `destructive`, `link` carry Figma tokens (gradient fills, accent link) | nova's palette is not this product's |
| `button.tsx` | `outline` uses shadcn's own `border-input` | `index.css` remaps `--border`/`--input` to `--line`, so the utility resolves to the reference-kanban hairline; the checkbox and radio keep a hard `border-border-checkbox-default` because that hairline is too faint for an unchecked control |
| `button.tsx` | new `soft` and `link-muted` variants | accent-tinted ghost, and the secondary link style |
| `button.tsx` | new `link` and `link-xs` sizes | inline text actions; shadcn's `link` variant keeps button height |
| `button.tsx` | BoardUI type ramp, radii and 20/18/14px icon sizes on `default`/`xs`/`lg`/`icon*` | matches the Figma scale |
| `button.tsx` | explicit vertical padding on `default` and `lg` | legacy CSS cancels the fixed height on composed buttons, which would otherwise collapse |
| `button.tsx` | disabled keeps pointer events; per-variant tokens do the dimming | restores the `title` hint on disabled controls and removes double fading |
| `button.tsx` | the cva base drops `text-sm font-medium` | `font-medium` is a different Tailwind class group from the composite `text-*` utilities, so tailwind-merge kept both and silently overrode `text-body-regular` on composed buttons; the size variants already carry the weight |
| `badge.tsx` | shape and type moved into a new `size` axis; 11 color variants added; BoardUI sizes drop the transparent border | one badge covers both Figma components, the counter pill and the status chip |
| `tooltip.tsx` | light card popup and matching arrow; positioner on `bui-tooltip-layer` | nova's inverted dark chip is not the design, and tooltips must clear dialogs |
| `dialog.tsx` | backdrop is an 18% text-primary tint, no blur | matches the Figma overlay |
| `popover.tsx` | positioner on `bui-popup-layer`; `anchor` forwarded | popovers opened from a dialog, and the date picker's external trigger |
| `checkbox.tsx`, `radio-group.tsx` | resting border `border-input` → `border-border-checkbox-default` | `--input` is the hairline; an unchecked control was invisible on a white card |
| `calendar.tsx` | day picker imported from `@daypicker/react` | same project as `react-day-picker`, and the one this repo already depends on |

## Data and interaction contracts

- Project selection scopes board requests and is retained in the URL and local preference. All projects includes tasks without a project.
- Board cards use `TaskCard`: a title zone over a footer zone. The footer shows the project, or a muted placeholder without one. An in-progress card is marked once its task has had no event for three days, and more strongly after seven. Task IDs stay in the detail drawer and list view.
- Read polling waits until the preceding request settles and discards responses after a view/filter change. Detail navigation keeps one drawer with Back history and ignores obsolete detail responses.
- The page makes no writes; the backend rejects every write request.

## Context and reading surfaces

Task context supports Markdown headings, lists, links and blockquotes. Local task links navigate within the drawer. Explicit formatting annotations use `CONTEXT_LAYOUT_QUESTION` in `src/lib/nawaban-model.ts`; the latest matching decision supplies presentation, while the original context and decision history remain available. Rendering never rewrites stored task data.

`src/styles/nawaban-typography.css` owns the shared reading hierarchy. Long titles, module names, tags and reference values retain complete text and destinations; `OverflowText` adds tooltips when their rendered text overflows. Full task details remain available by opening a card or row.

## Verification boundary

Run the commands in [README.md](README.md). Node tests cover data mapping, graph relationships, navigation, source provenance, date behavior and polling. Component tests cover control interaction, dialog dismissal, focus and selection. These fixtures do not establish full mobile/keyboard acceptance; those require separate integration checks against a database copy.
